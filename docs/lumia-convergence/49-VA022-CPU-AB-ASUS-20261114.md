# VA-02.2 — Kokoro CPU Thread A/B aislado (14-11-2026)

## Hallazgo físico confirmado en ASUS

**VA-02 baseline**, 4 frases fijas × 2 rondas: p50 1221.9 ms, p95 1599.7 ms. **VA-02.1 fase real**: 8 síntesis Kokoro residentes, p50 total **1332.9 ms** / ONNX **1325.2 ms** (~99.4% de la mediana total), p95 **1788.9 ms**, máximo ONNX **1780.4 ms**. G2P p50 **0.2 ms**, WAV 3.2 ms, cola **0**, lectura WAV **0.5 ms**. El tiempo de llamada e inferencia sí se mide; no se mide latencia de Chrome, Whisper o Qwen. El p95 sobre 8 muestras coincide con el máximo usando percentil nearest-rank. Diferencias entre ejecuciones VA-02 y VA-02.1 NO son regresión causal ni optimización.

La LUMIA diaria YA hace prefetch acotado: `VITE_LUMIA_TTS_PREFETCH_NEXT=1`, `VITE_LUMIA_FAST_FIRST_CHUNK=1`, y el worker ONNX residente serializa la inferencia en FIFO. No sugerir implementar de nuevo el prefetch. La medición secuencial `cola=0` no implica cola cero durante una conversación real.

## Razón para probar CPU threads

ONNX Runtime permite `SessionOptions.intra_op_num_threads` y el proyecto abierto `kokoro-onnx` documenta el uso de `Kokoro.from_session(session, voices)`. El óptimo depende de la CPU y carga del sistema; 2 o 4 hilos pueden mejorar, empeorar o no variar el tiempo. Referencias:
- https://onnxruntime.ai/docs/performance/tune-performance/threading.html
- https://github.com/thewh1teagle/kokoro-onnx/blob/main/examples/with_session.py

## Instrumento, límites y seguridad

**A/B exclusivamente en `LUMIA-VQ03-QA` y solo si el usuario lo inicia. NO cambia ni actualiza el modelo original ni el motor activo en LUMIA-ASUS.**

- `bridge/runtime/kokoro/resident.py`: si y solo si `ORBIA_VA022_CPU_AB=1`, en el arranque del worker permite `ORBIA_VA022_INTRA_THREADS=auto|2|4`. El modo auto usa la construcción original `Kokoro(MODEL,VOICES)`; los otros usan `onnxruntime.SessionOptions().intra_op_num_threads`, `ORT_SEQUENTIAL`, `CPUExecutionProvider` y `Kokoro.from_session`. No modifica el modelo ONNX, voz, peso, G2P ni procesamiento WAV. Si la versión local de `kokoro-onnx` no ofrece `from_session`, rechazar el perfil: **NO instalar nada por ahora**.
- `bridge/orbia/resident-tts.mjs`: el worker informa el conjunto real de proveedores en la respuesta `ready` solo durante A/B. El benchmark verifica CPU puro (si el baseline usa otra EP, falla en lugar de comparar peras con manzanas); mantiene la FIFO y cierra únicamente su propio worker antes de cambiar variante.
- `scripts/lumia-kokoro-cpu-ab-va022.mjs`: tres perfiles **auto, 2, 4**. Cada perfil crea su propio worker, precalienta, procesa las mismas **4 frases × 2 rondas**, lo cierra, registra p50, p95 y p50 ONNX y variación relativa. Comprueba longitud WAV dentro de 5%, exclusivamente para descartar alteraciones graves; **NO certifica fidelidad de timbre, ritmo ni igualdad byte a byte**. No graba ni reproduce el audio, no usa micrófono, no conserva WAV, no descarga modelos, no utiliza CUDA ni hace cambios a Windows. Puede cargar la CPU; cerrar todas las instancias de LUMIA antes de empezar. No inferir mejoras con solo 8 mediciones por variante ni cambiar automáticamente configuración diaria.
- `scripts/certify-lumia-va022-cpu-ab.mjs`: pruebas sintéticas de validación de proveedor y A/B sin voz real, regresión en CI Windows+Ubuntu y protección del original.
- La implementación de producción `LUMIA-ASUS` jamás añade las variables `ORBIA_VA022_CPU_AB` ni `ORBIA_VA022_INTRA_THREADS`; el perfil de audio original permanece intacto.
- Las opciones GPU (CUDA/TensorRT/DirectML) siguen **fuera de alcance**. Primero medir CPU con lo instalado, sin asumir que GTX 1650 Ti disponga de un proveedor GPU compatible.
